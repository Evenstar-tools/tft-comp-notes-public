# 数据更新规范

## 触发与分工

- 版本维护人确认新补丁实装后 30 分钟内核实赛季、队列、来源补丁、构建和生效时间，更新 `data/current-patch.json`，同步版本状态。依赖新赛季或新构建的目录、映射和采样模板一并复核。阵容样本仍在积累时标「待复核」。
- 数据维护人每天按北京时间核对来源时间，刷新已核实队列的数据。普通推荐至少 100 场，均名 ≤ 4.50 或登顶率 ≥ 15% 进推荐，达样本门槛且两项均未达标进次选。跨热补滚动窗口须注明覆盖范围。
- 攻略维护人核对本批体系、公开章节和终盘棋盘，再更新文案和核心样本。首页从有效原生体系自动取至少 100 场、原始均名 ≤ 4.40 的路线。首页合计最多 12 套。赌狗、84、95 各组随版本数据分配，单组最多 8 套。英雄强化最多 2 套，和站主置顶、补荐一起计入 12 套。不足 4 套时数据门禁提醒站主补荐。上一榜最多保留至热补实装后 12 小时，已有有效的当前构建批次时切换。
- 少量例外写入同构建的 `data/patch-recommendations.json`。每条用 `override` 设置 `pin`（置顶）、`include`（补入）或 `exclude`（撤下）。置顶可用整数 `pinOrder`，无样本卡可设 `manualBadge`，默认显示「站主推荐」。`note` 写判断依据。过时构建的例外自动失效。
- 来源空样本、队列错配、模型换代或门禁报错时暂停发布。编排器在采集、前置门禁或归档失败时恢复本轮自动更新的快照，保留复核输出。手工编辑的候选数据按本轮 Git 差异回退至上一份已核验内容。归档后若复验失败，保留候选现场，核对批次清单和三件套后重试。

## 定时数据发布

定时任务从同补丁的公开主线独立检出启动，使用已登录的 GitHub CLI。运行 `node scripts/run-conditional-refresh.mjs` 会先核查上游赛季、队列、补丁、模型和采样时间。PBE 还要求词表基础补丁及实际构建与站内完全一致。正式服以排位接口返回的补丁、模型和采样时间为准。条件不齐或没有数据变化时保留现有生产数据。`--dry-run` 显示预检结果及采集计划。

刷新只允许修改所选配置的战绩快照。带归档的回执在归档后复验通过才记录批次 ID，对应白名单允许修改 `data/stats-history.json` 并新增或修改本批 `public/stats-history/<batchId>/heroes.json` 和 `equipment.json`。其他历史批次、未授权路径及删除、重命名和已暂存变更均阻断，归档正文须与本轮快照一致。全部采集模块写出快照并通过数据门禁后生成本轮回执，快照内容相同可正常结束。回执缺项或快照未对齐时停止自动发布。候选头部提交通过 `domain-tests` 且主线仍是采集基线时才合入 `main`。自动任务随后比对正式域名的公开目录与首页数据时间，若尚未生效则报告生产读回失败并保留具体状态。新补丁、热补确认、体系绑定和攻略内容仍由人工审定。巡检命令为 `npm run data:alerts`。

词表构建领先站内时，核对 Riot 客户端清单、近期已结束的同区服标准对局实装记录，以及战绩源的补丁和采样时间。确认实际已切构建且仍属同一玩法补丁后，更新站内构建和实装时间，用 `--profile all` 首刷并通过门禁。三日窗口覆盖旧构建时保留跨构建标记，独立短窗按其实际构建保留。

GitHub Actions 错开整点运行。`fast` 在北京时间 03:17、09:17、15:17、21:17 更新体系与趋势。`daily` 在北京时间 10:53 运行，包含纹章并自动归档。也可从 `main` 手动预览或运行，条件刷新可显式传入 `--archive`，确保本轮同时采集英雄、常规装备和特殊装备。自动发布使用仓库 secret `DATA_REFRESH_TOKEN`，应为具有仓库内容与 PR 写权限、Actions 读权限的专用令牌，以便候选 PR 自动触发检查。手动预览无需该令牌。

## 模块和入口

文件 ID 即 `--module` 的值。路径相对于 `site/`。

| 数据（`data/<id>.json`） | 刷新脚本（`scripts/`） | 默认配置 |
| --- | --- | --- |
| `hero-stats` | `prepare-hero-stats.mjs` | daily、catalog |
| `item-wearers` | `prepare-ordinary-item-stats.mjs` | daily、catalog |
| `special-item-wearers` | `prepare-special-item-stats.mjs` | daily、catalog |
| `emblem-stats` | `prepare-emblem-stats.mjs` | daily、catalog |
| `trait-stats` | `refresh-trait-stats.py` | daily、catalog，使用攻略名次表的过滤条件 |
| `guide-placement` | `refresh-guide-distributions.py` | daily、guides |
| `guide-family-stats` | `refresh-guide-families.mjs` | daily、guides，同批更新趋势 |
| `guide-carry-stats` | `refresh-guide-carries.py` | daily、guides |
| `comp-trends` | `refresh-comp-trends.mjs` | daily、guides，也可单独读取已保存体系批次 |
| `patch-recommendations` | 人工维护推荐状态、构建和公开章节引用 | daily、guides 校验 |
| `patch-recommendation-stats` | 人工维护同构建短窗核心样本 | daily、guides 校验 |

`daily` 和 `all` 实采表中的九个自动模块。人工维护的推荐状态和同构建短窗仍走单独采样与复核。`--module` 可重复。离线巡检对同赛季同队列的较早纹章快照提示警告，自动日更要求本轮纹章样本已对齐。两份推荐数据保留生效前的旧构建时提示警告，当前推荐仍按构建检查。其他模块与当前赛季、队列、补丁或已声明的构建不符时拦截。

## 标准四步

在 `site/` 执行。离线检查使用 Node.js 和 Python 3。真实采集另需 Python 的 `requests`、`beautifulsoup4`，以及体系脚本使用的 Playwright 浏览器（Windows 为 Edge，其他平台为 Chromium）。

1. `npm run data:status` 查看采样时间、补丁、构建和记录数。机器读取用 `npm run --silent data:status -- --json`。攻略名次表只有日期精度。
2. `npm run data:refresh -- --profile daily --dry-run` 核对精确顺序。预览仅读本机入口并探测 Python。含体系刷新时，从当前站点的公开 `/api/guides/catalog` 导出同版目录，默认保存到 `outputs/family-review/catalog.json`，或用 `--catalog <文件>` 指定。切补丁时先将 `guide-placement.json` 的批次补丁、构建和适用 `edition` 对齐，保留独立观察的来源与时间。
3. `npm run data:refresh -- --profile daily --archive` 按当前队列刷新并归档。直接调用编排器时用 `--archive` 启用归档，条件刷新入口的 `daily` 自动启用。编排器先验收当前快照再归档，结束后复验。
4. `npm run data:verify` 核对最终候选并查看 Git 差异。门禁校验名次桶、公开引用、历史数据和补丁范围，报错时修正后重跑。

取数短窗用 MetaTFT Explorer，并核对实际响应。体系榜使用整数天窗口，`comps_stats` 的小数天参数可能回退到默认窗口。短窗覆盖实装切换且没有逐局构建证据时，标注为跨构建窗口。

## 队列切换和历史归档

- 采集渠道由 `current-patch.json` 的 `seasonId`、`metaTftPatch` 推导。`sN-pbe` 使用 PBE，`sN-live` 使用正式服排位（MetaTFT 请求队列 `1100`）。可选 `queue` 须与赛季一致，正式服接受 `RANKED`、`RANKED_TFT` 或 `1100`。正式服可用 `tierFilter` 指定逗号分隔的段位字符串或数组，例如 `["DIAMOND", "MASTER"]`，采集时发送 `rank`。无热补时 `bPatch` 为空，正式服可以省略。切服仍需人工对齐公开攻略目录、来源 ID、体系绑定和趋势基线。
- PBE 按北京时间数据日、赛季、补丁和构建留档。同日同补丁切到另一构建时，新归档 ID 追加构建号，保留原批次与原链接。同一构建只接纳采样时间不倒退的数据。正式服按赛季和补丁留档，同补丁用时间不倒退的采样覆盖原批次。相同批次重复归档复用原有路径。归档渠道与补丁默认从当前版本推导，也可用 `--channel ranked --patch 19.1` 显式核对正式服补丁。
- 三件套须为同队列、同补丁、同北京时间数据日及同滚动天数，采样时间须在补丁生效后。归档写入 `public/stats-history/<id>/` 的 `heroes.json`、`equipment.json`（含 `standard` 与 `special`）及 `data/stats-history.json`（零重复副本）。历史快照沿用当时的滚动窗口。
