# 阵容撰写、数据维护与发布迭代全流程规范

本文档是公开仓（`Evenstar-tools/tft-comp-notes-public`）所有**攻略撰写、棋盘结构、站位配装、成图导出、战绩录入与口径、日更热补、提 PR 与上线迭代**的唯一权威规范。公开仓根目录 [AGENTS.md](../../AGENTS.md) 仅保留协作入口与总指针；凡新增、修改或废止任何硬性规定，必须在同一 PR 同步更新本文件并通篇检查无冲突。

---

## 一、立项准入与原创署名

### 1. 准入标准（先查实战再立篇）
- **实盘验证**：新攻略或新变阵必须基于当前补丁、同队列同窗口的实战样本（MetaTFT／DataTFT／TFTable），明确剥离高费大成幸存者偏差与假独立赌狗（例如高能流行顺带追三星的挂件不单开赌狗篇）。
- **宁缺毋滥**：同类路线优先并入现有攻略作变阵；只有主 C 或核心体系显著不同、数据达标，或填补版本关键主 C 空白时才新开独立章节。
- **门槛简短人话前置**：依赖特殊解锁条件、专属英雄强化、必拿转职／神器或高经济的非常规阵容，首句用简短自然的人话直接点明进场或解锁条件（如「高经济速九才进…」「有 K/DA 纹章且 2-4 前刷 4 次开芬妮才进…」），**禁用 `【特殊运营门槛】` 等厚重方括号前缀**。

### 2. 外部原创署名规范
- **核实署名**：收录外部原创阵容先核实提出打法的人和作者原名，在攻略源文档单列署名，攻略页与导出的一图流沿用同一行。
- **格式统一**：B 站原创作者统一按 `B站：**作者名**` 署名（只加粗作者名）；其他来源沿用 `阵容原创：作者名`。
- **分工与命名**：转发、翻译、整理与变阵贡献者按实际贡献署名；多人共同开发按原作顺序记录；只贡献某个变阵的作者署在对应变阵；原作者未核实时只记已知来源，查实后再补。作者为构筑正式命名时在正文简要保留原名，仅用来搜索的口头别名放入 `site/domain/guide-slugs.ts` 的 `searchAliases`。
- **全程保留**：热补更新、改名、并入其他攻略或重新导图时必须保留原署名；默认只展示作者名，站主明确要求时再附视频链接；交付前分别打开攻略页和导出一图流核对署名。

## 二、攻略结构、ID 与路由规范

### 1. 命名与打法标签
- **标题短名**：用玩家熟悉的「羁绊＋主 C」短名（如「速八六舞者亚索永恩」「四古典烬」），不把 `84 / 95 / 慢搜` 混写进标题（已有约定俗成的 95 标题除外）。真正换主 C 的变阵用独立名字，仅补挂件的上限沿用原主 C。
- **打法独立块**：打法单独写一个文本块：`打法：84`、`打法：95` 或 `打法：X费慢搜`（分类与推荐分组、趋势筛选共用）。
- **统一游戏简中名**：羁绊通过稳定 ID 维护 `site/data/trait-reference.json` 的 `gameName`，旧译仅留作搜索别名，冲突一律以游戏内简中名为准；统一使用「解锁」等玩家常用术语。PBE 暂名和未公布数值保留来源，切正式服再校。

### 2. 稳定 ID 与语义短链（硬性规定）
- **`sectionId`**：新攻略直接用简短、唯一的英文 kebab-case slug 作为 `sectionId`（如 `true-damage-akali`），并在 [site/domain/guide-slugs.ts](../domain/guide-slugs.ts) 登记同名公开 slug 及 `searchAliases`。**禁止再手编 `sample-block-NNNN`**。
- **`teamId` 与 `instanceId`**：新棋盘和每枚棋子（含替补）一律用 [createId()](../domain/id.ts) / 标准 UUID v4 生成，并在 `site/domain/guide-slugs.ts` 为每张棋盘配置攻略内唯一、能辨认人口或变阵的短名（如 `lv6`、`lv8`、`lv9-nidalee`、`lv8-ashe`）。**禁止再用顺排假 UUID**（如 `00000000-0000-4000-8000-00000000XXXX`）。
- **ID 稳定性**：已发布的内部 ID 和公开短名保持稳定；战绩、快照与本机存档继续用内部 ID，公开链接统一通过 `canonicalGuidePath` / `guideLink` 生成。合并或更名旧攻略时在 `site/domain/legacy-guide-redirects.ts` 保留 308 永久跳转。

### 3. 数据结构与默认盘规则
- **`public-preview.json` 镜像同步**：新增或修改攻略时，必须同步维护 `section.teams`、`section.team`（与主盘一致的镜像）、`section.primaryTeamId`、`section.stageTeamIds`（过渡或升人口上限盘 ID 列表）及 `section.summaryBlockId`（首页与列表首段摘要块 ID）。**严禁重复写入同赛季 `section.gameData`**（由 `verify-public-release.py` 强制拦截）。
- **同一路线按运营节奏选默认盘**：慢搜优先开停级能打的棋盘（一费 5 级、二费 6 级、三费 7 级），84 优先开八级成型盘，95 优先开九级成型盘；高人口上限单独切换。一条主线的前、中、后期最多 3 张阶段盘，独立变阵单独切换。
- **并列变阵按本版表现选主阵**：同篇攻略里有独立成型的羁绊或构筑分支时，用本版同队列、同批次、同时窗、同口径的体系样本比较；在场数达标且符合本版推荐条件的分支中，均名最低的一支作默认主阵，其余保留为变阵；可比样本不足时沿用已复核主阵。
- **含 5 费弈子攻略必含 9 级盘与 9 级结算排名**：凡录入包含 5 费弈子的攻略，**必须配备 9 级成型／上限盘及对应的 9 级固定结算排名查询可选**，确保玩家可在棋盘下方「上人口与补卡对照」直接比较停级与上九的结算排名。

## 三、正文撰写规范（必写内容与去废话硬规）

### 1. 正文只写「棋盘上看不出来的 5 类决策信息」
每条 1–2 句短句，沿用 S16 极简短句风格，按对局决策顺序排列：
1. **进场条件**：什么散件、开局来牌、海克斯或解锁节奏适合玩，什么情况别硬玩；
2. **前期过渡与接装**：谁打工带输出装／肉装，几级或几星换主 C／主坦接装，余装和功能装怎么分；
3. **搜牌与停牌节点**：几级启动、停哪级追谁三星（只给关键追三棋子标 3★），或几星停 D 存钱上人口；
4. **解锁、换人与上限补位**：关键解锁条件（写清准确数字／机制）、缺核心时谁先顶、拉高人口或有转职时怎么变阵；
5. **高价值实战细节与避坑**：真正左右胜负的机制（如必须同侧破甲、绝不死停某级、禁止合某件负提升装备）。

### 2. 必配结构化配装块（供程序解析与审计）
每张棋盘必须在章节末尾 `各棋盘配装` 标题下配一个结构化文本块，格式如下，角色与成装正式名必须与该棋盘数据 **100% 一致**：

```text
棋盘配装 · <棋盘名>
主C：<弈子正式名>。<成装1>、<成装2>、<成装3>。
主坦：<弈子正式名>。<成装1>、<成装2>、<成装3>。
副C：<弈子正式名>。<成装1>、<成装2>、<成装3>。
功能装：<弈子正式名>。<功能装>。
```

### 3. 五类绝对禁止清单（废话与防御性话术黑名单）
1. **禁复述棋盘可见内容与车轱辘重复**：不报菜名式列全员名单或棋盘已拼好的羁绊串，不逐字重抄棋盘已画好的站位和三件套（隐藏的 `棋盘配装` 块除外）；首段与下文、正文与棋盘 `notes` 不得逐字复述同一条规则；正文装备替代用玩家短称（青龙刀、羊刀、血手、帽子、死刃等）。
2. **禁作者闲聊与口头外号叙事**：正文禁止写「作者把这套叫……」「作者示范……」「原视频称……」等无关叙事；原创署名只留在独立署名行，搜索用口头外号放 `guide-slugs.ts` 的 `searchAliases`。
3. **禁情绪口水与营销空话**：禁用「版本最强」「上分密码」「极其强势」「吃分稳定」「成型即可吃鸡」「综合强度拉满」「这套阵容的核心思路是……」「总的来说……」等零信息量措辞。
4. **禁防御性免责与正确废话**（给建议必须带**具体触发条件、具体棋子名或具体装备名**）：
   - ✗「视对局／来牌灵活调整」→ ✓「盖伦未二星、蕾欧娜先两星时直接互换接肉装开 2 护卫」
   - ✗「血量健康上九，血量不健康多搜」→ ✓「八级亚索、永恩双两星稳血再存钱上九，五阶段未二星留在八级搜满质量」
   - ✗「装备不对可换类似替代装」→ ✓「无尽可换破防链枷，别做青龙刀」
   - ✗「同行多建议转阵」「以上站位仅为示意，实战请根据对手调整」「仅供参考」→ 直接删除。
5. **禁写死过时战绩与视频平台外链**：正文不得手写易过期的旧补丁场数／均名（带规范链接的当期固定盘样本句除外）；严禁在正文、富文本链接或 `notes` 中残留 B 站、抖音、YouTube 等视频平台外链（由 `audit-guide-boards.mjs` 自动拦截）。

## 四、棋盘配装、站位硬门禁与同格替补

全站所有公开攻略棋盘须通过 `npm run guides:audit -- --all --strict` 与 `guide-board-audit.test.mjs`（**0 错误 0 提示**）：

### 1. 配装硬门禁
- 每张公开棋盘必须明确标注上场 `主C`（或 `主输出`）与 `主坦`；
- **主 C 与主坦必须配满 3 件非散件成装**（或单件 `窃贼手套` `TFT_Item_ThiefsGloves`）；副 C 与功能装按实战补齐；
- 所有 `unitId`、`itemId`（含替补）必须在当前 `season.json` 合法名单内。

### 2. 站位坐标硬门禁（4 排 7 列，`pos 0..27`）
棋盘第 1 排为 `0–6`（前排，左起），第 2 排为 `7–13`，第 3 排为 `14–20`，第 4 排为 `21–27`（底排）：
- **远程主 C（射程 ≥ 4）**：默认站第四排底角（`21` 或 `27`）；双远程主力有装时分守两角，技能／功能装需同侧集火时同边摆；
- **近战输出（射程 ≤ 2）**：优先站第二排侧翼（`7/8` 或 `12/13`）；
- **石像鬼主坦**：站第一排单顶或半单顶，**左右两格不得同时被友军占用**；第一排尽量不超过 3 名棋子，前排多时错开副坦；
- **阿木木主坦专属硬规**：必须站第一排右数第三格（`pos 4`）、独占第一排、相邻格（`3、5、10、11`）全部留空，主 C 站同侧外沿（远程 `27`、近战 `12/13`）；
- **破甲／减抗一致性**：薄暮法袍（`TFT_Item_SpectralGauntlet`）或离子火花（`TFT_Item_IonicSpark`）前排持有者必须与主 C 同侧；前排带薄暮时，主 C **不得再带最后的轻语**（`TFT_Item_LastWhisper`）重复破甲；
- **乐器与召唤物**：海之歌乐器、3 摇滚恶魔自动生成的地狱偶像等不得越界或与上场棋子重叠。

### 3. 编辑器放置与同格替补规则
- 从下方棋子架拖到已占棋格时成为该格替补；棋盘内拖到已占格交换站位，拖到空格移动；点击小头像同格换上替补，拖小头像到空格拆开；拖动提示保持一行固定高度不抖动。
- **叠放上限与唯一性**：每格最多叠 1 枚替补，**每盘最多 2 个叠放替补**；替补不得与在场或其他替补重复，且具备独立 UUID v4 `instanceId`；人口和羁绊按当前大头像计算，两枚棋子的星级与装备各自归属。

## 五、阵容图、一图流生成与成图验收

### 1. 一图流生成方式
- **命令行导出**（在 `site/` 目录执行，支持快速图 `quick` 与含阶段过渡的完整图 `full`）：
  ```powershell
  node scripts/export-guide-poster.mjs <攻略链接> [--board 棋盘名或UUID] [--format quick|full] [--stage 阶段名] [--out 输出PNG路径] [--channel msedge]
  ```
  - 完整攻略 `full` 最多附加 2 张过渡棋盘；网页端也可直接在攻略 URL 后加 `&poster=1` 预览与下载；预览、主动导出与用户下载必须对应同一选中方案。
- **手机阅读优先**：按手机实际阅读尺寸排版，首看当前棋盘和主 C、主坦、功能装，完整攻略按对局顺序选入必要阶段；站位、星级、装备、手动摆过的乐器、海克斯全名（标明必选／可选）与原创署名随当前棋盘导出。

### 2. 阵容图里的同格替补与图注
- **视觉排布**：沿用 [Board.tsx](../components/Board.tsx) 叠放样式——当前上场棋子用大头像，替补用圆形小头像叠在同一格**左上角**，保留各自费用描边，避免挡住主棋子姓名、星级或装备。制作换人后站位图时，将换上来的棋子放大、换下的缩到左上角；两套站位不同则分别出图。
- **换人图注用词**：需要交代过渡、解锁或变阵换人时，图下统一写「**A 替换 B**」（上场在前、换下在后，如「梅尔替换史密奇」），涉及解锁条件或换回时机在棋盘旁补一句，普通站位图省略；「叠放」仅用于说明编辑器操作或头像排布。
- **成图必检**：交付前必须打开实际 PNG 按手机尺寸逐项核对格位、头像层级、装备归属、原创署名与替换方向；若常规 PNG 导出漏掉小头像，使用保留叠放的编辑器棋盘截图或按同格式补画后再交付。

## 六、数据录入、两层口径与推荐／趋势规则

### 1. 数据文件分工与采集来源
| 数据层 | 权威文件 | 采集脚本与来源 | 口径说明 |
| --- | --- | --- | --- |
| 原生体系战绩 | `site/data/guide-family-map.json`<br>`site/data/guide-family-stats.json` | `scripts/refresh-guide-families.mjs`<br>MetaTFT `comps_data` + `comps_stats` | 按模型原生聚类，含所有结算人口（含死在 7/8 级），**无幸存者偏差** |
| 固定终盘 & 全人口核心 | `site/data/guide-placement.json` | `scripts/refresh-guide-distributions.py`<br>MetaTFT Explorer（`tab=comps` 固定名单 / `tab=units` 核心） | 固定终盘锁结算人口+完整名单+无转职/人口装/重复子；核心样本不锁结算人口 |
| 主 C 三件套配装 | `site/data/guide-carry-queries.json`<br>`site/data/guide-carry-stats.json` | `scripts/refresh-guide-carry-stats.py`（或对应日更流程） | 4–5 费主 C 查二星三件，1–3 费慢搜查三星三件 |
| 阵容趋势归档 | `site/data/comp-trends.json` | `scripts/refresh-comp-trends.mjs` | 随体系刷新自动追加 UTC 观测批次，换主盘通过 `families` 连续接续 |

- **交叉核实与留痕**：MetaTFT／DataTFT 查实战样本，TFTable 比变阵，TFTFlow 核机制过渡，NoxuTFT 查海克斯，需要复算终盘时用猫咪 TFT 交叉验证；所有样本保留赛季、补丁、区服、时间窗、星级、装备数、场数及原查询 URL。
- **口径严禁混算**：
  - 固定终盘按结算等级和完整名单取样；只要求成员同场的查询归入「核心与装备」（即便列全了九名英雄）；
  - 双核心子集对比母样本时，仅在同批、同条件且可验证子集时逐名次桶相减；
  - 常规小样本（`< 100` 场）中，固定终盘有完整且与场数吻合的 8 桶分布时显示均名、前四率、登顶率并标注「少量样本」，其余常规小样本只显示场数；英雄强化小样本保留场数与口径。

### 2. 攻略页两层数据口径铁律
- **顶部均名 & 右侧「对局表现快览」= 与外面卡片 100% 一致**：
  - 只展示当前体系的**原生体系均名**；
  - 无原生体系聚类时，仅回退同套共享的当前补丁 **≥ 100 场全人口核心样本**（`core`／`lineup`），切换阶段盘不跳变；
  - **严禁**将单人口固定结算名次（如 8 级／9 级结算）或少量历史样本放到顶部冒充整套均名。
- **顶部「同套变种」**：按独立体系比较，取当前可比较的体系均名从好到差排序；色阶为 `< 4.00` 绿、`4.00–4.50` 琥珀、`> 4.50` 红；缺少对应体系样本时标「暂无体系数据」。
- **棋盘下方「上人口与补卡对照」**：专门展示同一体系不同等级与同人口补卡的**固定结算样本**（标清停级、同人口补卡、历史或同装口径）；若所有行均无有效样本则隐藏对照模块，不占空壳。

### 3. 首页推荐、全部攻略分档与阵容趋势规则
- **全部攻略分档与「数据对照」**：当前有效批次样本 `≥ 100` 场，体系均名 `≤ 4.50` **或登顶率 ≥ 15%** 进「推荐」，其余达样本门槛的进「次选」；无原生体系时可用同构建核心样本（标「核心样本」）；缺样本、版本过期或待复核进「待复核」；英雄强化保留独立入口。「数据对照」主表收全部已绑定原生体系（含同分母出场率），主表下方独立展示「核心样本对照」区，自动纳入未绑定原生聚类但拥有当期非历史 `≥ 100` 场全人口核心样本的常规攻略（出场率列留 `—`，避免跨口径混排）。
- **首页本版推荐**：仅用当前有效批次 MetaTFT 原生体系自动入榜（`≥ 100` 场且原始均名 `≤ 4.40`）；合计最多 12 套（含英雄强化与站主手选／置顶），单组最多 8 套、英雄强化最多 2 套，同篇同组择优一席按均名／场数排序；不足 4 套时门禁提醒站主补荐；站主置顶／补入／撤下仅对当前构建有效；热补后最多保留 12 小时「上一版参考」。
- **阵容趋势**：
  - 只绘制「综合表现」单一主曲线：均名 `4.90→3.50`（55%）、登顶率 `6%→24%`（25%）、前四率 `42%→68%`（20%）归一组成质量分（占 82%），加 18% 受均名门控的对数样本分 `log10(max(100, 场数)/100)/3`，范围限定 `0–1`，跨日绝对可比；
  - 费用筛选按同盘同体系已核实的携装输出位归档，5 费及以上合为一档，每页最多 10 套；体系映射与采集共用核心锚点，供筛选的副 C 存于趋势归档；换主盘通过 `families` 关联；版本节点按 `patch` 去重，晚于首日新收录的体系在首点标「首次收录起点」线头。

## 七、日常更新、版本迭代与版本页规范

### 1. 日常与版本数据更新（详见 [数据更新规范](数据更新规范.md)）
在 `site/` 目录下统一走编排脚本：
- `npm run data:status`：查看 11 个数据模块的补丁、构建、北京时间与对齐状态；
- `npm run data:refresh -- --profile fast|daily|all [--archive]`：按档位自动刷新，带文件锁与门禁失败自动回滚；
- `npm run data:verify`：运行离线全量数据完整性门禁；
- `npm run data:alerts`：巡检上游新版本／构建／模型、绑定缺失与首页推荐异常。

### 2. 版本更新与热补迭代流程
1. **核实实装基准**：确认 Riot PBE／正式服实际构建号、补丁与生效时间，更新 `site/data/current-patch.json`；
2. **编写版本更新页（`site/data/patch-notes.ts`）**：
   - **改动明细完整保留**：`groups` 下全部数值改动明细按分类完整陈列，不因精简摘要误删条目；
   - **顶部要点分类划重点**：以 `解锁：`、`削弱：`、`加强：`、`装备与海克斯：`、`小结：` 短标签起笔，严禁写入客户端杂项或重复首页推荐摘要；
   - **环境观察 2–3 句**：只写影响选线与节奏的核心变化，不写纯构建运维日志；
   - **阵容观察 4–8 套、不跳外站**：`PatchReference.impacts` 精选直接受削弱／加强影响的 4–8 套阵容（标 `buff`／`nerf`／`adjust`），每条 1–2 句直写影响与应对，**禁止附外跳「战绩 ↗」链接**（点击阵容名直达本站攻略）；
3. **刷新数据与复核异动**：执行全量刷新，重点复核均名变动 `≥ 0.25` 或登场变动 `≥ 0.10` 的体系，核对 `guide-family-map.json` 挂件微调或新模型重配；滚动窗口跨热补时标注 `spansBuilds: true`；
4. **基线对账与防倒退**：
   - 同批统计的采样时间不得倒退；
   - 任何已发布攻略、棋盘、当期固定样本或同模型体系的减少，必须在 PR 说明中逐一列出稳定 ID 和原因；
   - 自动刷新只接受所选配置全部采集并校验通过的回执。

### 3. 攻略内容迭代规则
- **修改现有棋盘**：保留原 `sectionId` 与 `teamId`，同步更新 `public-preview.json` 的 `teams`/`team`、`棋盘配装` 块与受影响的 `guide-placement.json` 名单查询；
- **新增变阵或阶段盘**：按第二节生成新 UUID v4 并在 `guide-slugs.ts` 登记短名，补齐 `棋盘配装` 与对应战绩查询；
- **换主阵／合并／退役**：换主阵后核对默认入口、首页与全部攻略主卡以及显式变阵旧链；合并或下线旧攻略时保留 308 跳转与搜索别名，清理悬空引用；
- **站主原盘发布边界**：带棋盘参数的旧链接保留指定棋盘；未指定棋盘且有可写数据库时，若默认落在系统临时盘则优先打开已保存、可发布的原盘。

## 八、提交、门禁、提 PR 与上线验收全流程

所有改动统一在公开仓（`Evenstar-tools/tft-comp-notes-public`）基于最新 `origin/main` 完成，严禁双份手工维护或跳过门禁直接推主线：

### Step 1：建干净分支与同步目录
```powershell
git fetch origin --prune
git checkout -b <feat|fix|docs>/<简短主题> origin/main
# 改动攻略或棋盘后，先刷新导出目录：
cd site
node scripts/export-family-catalog.mjs
```

### Step 2：本地全套硬门禁（必须全部退出码 0）
在 `site/` 目录依次执行：
1. **全站攻略棋盘与文案严格审计**（涉及攻略／棋盘／配装／文案必跑）：
   ```powershell
   npm run guides:audit -- --all --strict
   ```
   要求 **0 错误、0 提示**。
2. **四合一综合门禁**：
   ```powershell
   npm run check
   ```
   自动串行执行 `tsc --noEmit` → 全量单测 → `verify-public-release.py`（脱敏、防泄漏、资源检查、去重 `gameData`）→ `verify-data-integrity.py`（11 数据模块、280+ 组 8 桶分布、绑定双向对账、推荐红线）。
3. **巡检告警核对**（涉及数据刷新或绑定调整必跑）：
   ```powershell
   npm run data:alerts
   ```
4. **生产构建验证**（与 EdgeOne Pages 生产一致）：
   ```powershell
   npx next build --webpack
   ```
5. **界面与成图实拍验收**（涉及 UI、布局、一图流或重点攻略必做）：启动本地 `npm run start`，用 Playwright 实测 `1440×900` 桌面与 `390×844` 手机端（无横向溢出、无控制台报错、视觉肉眼核对）；导出 PNG 一图流按手机尺寸开图检查。

### Step 3：提交与提 PR
- **精准暂存**：只 `git add` 本轮明确修改的文件，**严禁 `git add -A`**（避免误带临时截图、未跟踪目录或缓存文件）；
- **PR 说明必含**：改动摘要、涉及的新增／修改／删减稳定 ID（凡删减或迁出已发布攻略／棋盘，必须在 PR 正文逐项按 `- retire \`guide:<sectionId>\` — 原因` 或 `- retire \`board:<sectionId>/<teamId>\` — 原因` 格式声明，否则会被云端 `verify-data-integrity.py --base` 阻断）、上述门禁的真实执行结果；
- **云端 CI 绿灯后合并**：等待 GitHub Actions `domain-tests`（TypeScript + 全量单测 + `verify-public-release` + `verify-data-integrity` + `next build --webpack`）全绿后 **Squash Merge** 入 `main`，自动触发 EdgeOne 生产部署。

### Step 4：上线后正式域名读回与收尾
1. 等待 EdgeOne 生产部署切换生效后，读回正式站 `https://tftnotes.com`（**开发与验收访问一律追加 `?rum_ignore=1`**，防止污染腾讯云 RUM 埋点）；
2. 涉及攻略新增、改盘或大批量更新时，运行线上验收脚本逐盘核对目录、渲染、短链与搜索直达：
   ```powershell
   node scripts/verify-live-guides.mjs --origin https://tftnotes.com --guide <sectionSlug>
   ```
3. 本地切回主跟踪分支快进对齐 `origin/main`，删除已合并的临时开发分支，并在跨线程统一台账记录合并提交、CI 与线上读回证据。
