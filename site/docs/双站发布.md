# 双站发布

本仓库是代码维护入口。GPTsite 是站主的私有编辑和预览入口，EdgeOne 是面对访客的站点。代码版本、攻略发布快照和战绩数据批次各自有版本，发布记录应写出实际验过的版本。

## 代码更新

1. 从本仓库的 `main` 开分支，改共用页面与业务逻辑。在 EdgeOne 输出里保留 Next.js 构建与游客在浏览器存档的入口。在 GPTsite 输出里保留 Sites 的 Worker 构建清单、站主登录及既有数据绑定。
2. 本地通过 `npm test` 和 `npm run build` 后开 PR。合入 `main` 后用 Makers 的部署记录核对实际构建提交。若自动部署未出现，在同一个项目的「新建部署」选 `main` 最新提交。
3. GPTsite 的同批更新由站主或获授权的维护者在原 Sites 项目发布。让两端取用同一份可移植改动，保留各自的部署适配，再记录公开 Git 提交和 Sites 版本。合入 GitHub 后，Sites 仍需独立构建并发布。
4. 打开目标版本的真实站点验证。EdgeOne 用游客入口检查首页、攻略、编辑器与保存重开。GPTsite 用站主账号核对站内内容与编辑发布界面。

## 从 GPTsite 更新公开阵容

1. 站主在 GPTsite 编辑、校对和发布选中的章节。只取发布管理的当前 `live` 快照，确认发布时间与章节数。同步站位和战绩的代码或数据表，可以在同一 PR 里交付。
2. 私下留存原快照与现有 ID 映射。沿用同一映射，公开攻略和棋盘的链接才能继续对应原方案。只把命令生成的公开快照加入 Git。

   ```sh
   cd site
   python scripts/prepare-public-snapshot.py --published /private/published.json --aliases /private/public-id-map.json --out data/public-preview.json
   ```

3. 同一张棋盘的配图可从公开棋盘重新生成。若章节含单独发表的配图，先检查素材及其公开权限，再补入公开素材并核对成图。原草稿、飞书内部链接、旧媒体令牌、私有 ID 映射和凭据存放在工作区的私有位置。
4. 核对快照时间、章节数，以及改动阵容的格位、星级、装备和一图流，再合入 `main`。现有无数据库版本从 `data/public-preview.json` 读公开内容。启用站主云端数据库后，公开快照要经过数据库自己的发布步骤。完整备份导入用于迁移或恢复。

数据库、媒体存储与游客本地存档保持独立。若公开部署失败，先在 Makers 核对日志与对应 Git 提交。若已发布内容需要撤回，向 `main` 提交恢复快照的 PR，并在成功部署后读回公开页。
